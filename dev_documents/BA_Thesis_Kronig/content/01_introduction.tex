\section{Motivation}
Mobile applications (apps) can have a variety of vulnerabilities. Modern Android apps have, on average, a surprisingly large number of vulnerabilities, which greatly impacts their security and usage \todo{Add any of the papers read here that say this}. Because of this, it is of great importance to have tools that can detect vulnerabilities, both statically by inspecting the code and dynamically by executing the code and inspecting it at runtime. There exists a diverse landscape of such Static Security Application Testing (SAST) and Dynamic Security Application Testing (DAST) tools. But how can the effectiveness and accuracy of these tools be measured and compared to one another? 

To measure the effectiveness of a tool, it is just as important to know how many security vulnerabilities the tool was not able to detect, as it is important to find the vulnerabilities themselves. Since most real-world mobile apps are closed source \todo{Probably add source for this}, there is no ground truth against which the performance of a security analysis tool on such apps can be evaluated, making it impossible to use them for measuring the effectiveness of such tools. To effectively measure and compare the accuracy of existing analysis tools, they have to be evaluated on intentionally vulnerable apps, of which the existing vulnerabilities are known to the person conducting the tests. 

One such dataset of intentionally vulnerable apps is hosted by OWASP Mobile Application Security Testing Guide (MASTG) \cite{owasp_reference_app_website}. The OWASP MASTG is an industry standard manual for testing and evaluating the security of mobile applications. As part of the OWASP Mobile Application Security (MAS) project, it contains a set of intentionally vulnerable apps that serve as educational reference material for the MASTG. The vulnerabilities that the MASTG is designed for are laid out in the OWASP Mobile Application Security Weakness Enumeration (MASWE). The issue with many of these apps is either a lack of publicly available source code and/or a lack of documentation of the implemented vulnerabilities, making them unfit for benchmarking vulnerability assessment tools. Most of them are not being actively maintained and are based on older Android versions, further reducing their value as both a learning resource for mobile developers and as a dataset for evaluating security testing tools. The goal of this BA thesis is to develop our own intentionally vulnerable OWASP MASTG reference apps, which can then be used as a mobile security teaching resource and for evaluating and benchmarking DAST and SAST tools. \todo{Make this last sentence nicer without two "and"s}

\section{Problem statement}
To make the apps usable for benchmarking both DAST and SAST tools, the apps will include an overview of every implemented vulnerability. To make the apps a valuable resource for learning about OWASP MAS as well as penetration testing, the apps will include descriptions detailing each implemented vulnerability. These descriptions will include what the vulnerabilities consist of, where they can be found in the code, how they can be exploited, and, depending on the vulnerability, how they can be fixed. These vulnerabilities are then mapped to their OWASP MASWE counterparts. To ensure that the apps adhere to the standards expected of OWASP MASTG reference apps, an analysis of the existing reference apps is performed to assess the state-of-the-art in OWASP MASTG reference apps. A literature review is conducted to determine the value and use case of the OWASP MASTG and its related fields for the academic world by analyzing and reviewing 22 papers that deal with the subject. Once the apps are developed, a comparison is established between them and existing MASTG reference apps, and the contribution made through the newly developed apps is evaluated.

\section{Objectives of the Thesis}
The objectives of this thesis largely concern developing multiple open-source OWASP MASTG reference apps that include both static and dynamic security vulnerabilities. The goal is to cover multiple OWASP MASVS vulnerability categories, focusing on vulnerabilities that have seen little to no coverage in existing OWASP MASTG reference apps. The documentation of the implemented vulnerabilities should be thorough and include: the overall list of implemented vulnerabilities, the mapping to their respective OWASP MASWE counterparts, and a detailed explanation for each vulnerability, documenting where it can be found, how it has been implemented, and how it can be exploited.

The thesis will include an analysis of existing OWASP MASTG reference apps, as to figure out the state-of-the-art in intentionally vulnerable Android app design. This allows us to ensure the newly developed apps adhere to the same standard. From this analysis it can be understood which vulnerabilities have so far seen little to no coverage, and are of interest for our implementation. \section{Structure of the Thesis}

This thesis is structured as follows. Chapter~1 introduces the subject of the thesis, the motivation behind it, its objectives, and the method for achieving them. In Chapter~2, we discuss the methodology and findings of both the literature review and the analysis of the state-of-the-art in existing OWASP MASTG reference apps. Chapter~3 provides essential background knowledge on key Android concepts and the OWASP MAS ecosystem, which are discussed and used in this thesis. Chapter~4 discusses the design for developing the reference apps, including design decisions regarding vulnerability selection as well as system architecture. In Chapter~5, each vulnerability implemented is covered in greater detail, supplemented with code snippets, implementation decisions, and challenges faced during their development. Chapter~6 concerns itself with the results of our work, comparing our developed reference apps with the existing MASTG catalog and assessing the contributions made. Chapter~7 discusses possible threats to the validity of our work, as well as any problems left open or newly discovered. In Chapter~8, we look forward to future work, outlining how this thesis could be extended upon. Chapter~9 then closes out the thesis.
