\section{System Architecture}

\subsection{System Architecture Overview}

A modular, multi-app system architecture is used for the overarching structure of this Android project \todo{Maybe replace this "this Android project" wording with something better}. The implemented MASWE vulnerabilities are grouped by their respective MASVS category. This means that all implemented vulnerabilities of the category MASVS-STORAGE are part of the same module \texttt{maswe\_storage}, whereas the vulnerabilities from the MASVS-CRYPTO category make up their own \texttt{maswe\_crypto} module. 

Each module is its own Gradle Module, with its own AndroidManifest, activities, services, backup rules, and launcher activity. The advantage of this is a clean and structured separation of the different implementations by category. The categories can be tested and used independently from each other, and vulnerabilities that affect the AndroidManifest are contained to affect only other vulnerabilities of the same category, instead of all of them. Without this, a MASVS-PLATFORM vulnerability that sets the app to debuggable in the AndroidManifest would result in all vulnerabilities having to include this debuggable vulnerability.

To minimize the amount of redundancies we use a Shared-Library approach. This means that all independent MASVS app modules make use of the same \texttt{common} Android library module, which has a \texttt{res} folder containing the resource values shared by all apps. This includes values in regards to layout spacing, strings, string font sizes, and color values. The \texttt{common} library module also includes layouts shared by all apps and asbtract activity templates, as discussed in the next subsection. \subsection{Feature-oriented Structure after OWASP MASVS}

Each app module is structured as follows. The launcher activity functions as the overview and hub from which all implemented vulnerabilities of the respective category can be chosen from. The vulnerabilities themselves are grouped into separate packages. These packages include all activities, services and other Java files that are part of the vulnerability's code. This includes for all vulnerabilties: a main activity serving as the vulnerability's starting point, as well as a \texttt{RegisterActivity.java}, \texttt{LoginActivity.java} and a \texttt{ProfileActivity.java}, that are used for user registration and login. This architecture is extended with other files depending on the vulnerability and its implementation, such as an \texttt{EncryptionHandler.java} which deals with cryptographic services. A high-level model of this structure can be seen in \ref{fig:high_level_view_feature_oriented_project_structure}.

This architecture further reinforces the clean separation and structure of the Android project. We package and isolate the code for each vulnerability's implementation, and group the vulnerabilities themselves by their respective categories. This creates a clear and intuitive overview of what vulnerabilities have been implemented, and where their code can be found. It allows for isolated implementing, analyzing and testing of each vulnerability. This benefits both the development process of the apps as well as the usefulness and usability of the apps.

\subsection{Template Based Activity-Architecture}
We make use of custom templates to heavily reduce the amount of boilerplate code. All of our vulnerability implementations require a starting activity, as well as a register, login and profile activity. Between the different vulnerabilities these differ in code logic but are (almost all) identical in layout. Because of this, the \texttt{common} library module includes four layout templates fitted with uniform styling and the basic navigating buttons and user input fields expected of them.  

The activities themselves share a lot of similarities and thus boilerplacte code as well. For example, many of the MASVS-CRYPTO vulnerabilities only differ in the concrete implementation of cryptographic operations, but are otherwise identical with each other as well as with vulnerabilities of other categories. To make use of these shared pieces of logic and remove redundancies, the \texttt{common} module includes three abstract activity templates that all activities make use of. The first is \texttt{BaseActivityTemplate.java} that all activities use, and the other two templates build on. The other two activity templates used are \texttt{BaseRegisterActivity.java} and \texttt{BaseLoginActivity.java}. The way this inheritance works is shown in the high-level model seen in \ref{fig:high_level_model_inheritance_templating}.

\subsubsection{Base Register Activity}
\texttt{BaseRegisterActivity.java} builds upon the \texttt{BaseActivityTemplate.java} and extends it with the register code logic shared by all vulnerability implementations. This logic consists of handling and sanitizing user inputs, potentially encrypting the user password, and saving the newly registered user credentials in JSON format to a designated Shared Preferences file. A flow diagram of this template can be seen in \ref{fig:base_register_activity_template_flow_diagram}.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=1.0\textwidth]{dev_documents/BA_Thesis_Kronig/figures/design/BaseRegisterActivity_Template_Flow.png}
  \caption{Flow diagram of the register activity template}
  \label{fig:base_register_activity_template_flow_diagram}
\end{figure}

Any inheriting register activity only has to implement the abstract getters for the concrete layout id and UI buttons. All other code is handled by the abstract class. The advantage of this is clear, as it greatly reduces boilerplate code. The template provides two different hooks. The first allows the inheriting register activity to add custom encryption to the user credentials before storing them. This hook is where different MASVS-CRYPTO vulnerabilities add their vulnerable encryption methods. The second allows for custom post-registration process.


\subsubsection{Base Login Activity}
\texttt{BaseLoginActivity.java} builds upon \texttt{BaseActivityTemplate.java} in a similar fashion to \texttt{BaseRegisterActivity.java}, as can be seen in its flow diagram here \ref{fig:base_login_activity_template_flow_diagram}. It requires the inheriting activity class to set the same getters as the login activity template, which are specific to each login activity implementation. It deals with setting up the activity and its UI elements, sanitizing the user input, and loading the stored user credentials. It goes on to possibly decrypting the stored credentials, before comparing them to the user input and directing the user to the specified target activity if the login attempt is successful.

It provides five different hook methods. They allow the inheriting login activity classes to specify the path of the file containing the user credentials and adding custom decryption to the stored credentials. The subclasses can furthermore customize how the password verification process looks like and what the activity should do upon a login attempt failing. 


\section{Frameworks and Technologies}
The apps are developed using native Android development in Java 11 and targeting API level 35, which translates to Android 15. The reason behind aiming for such a high API is that many of the existing MASTG reference apps suffer from being outdated, having not received any updates or maintenance in years. Because the OWASP MAS project is constantly evolving alongside the Android ecosystem, it would not make much sense to develop apps for an older Android version than the one the standard is based on, since the apps are supposed to be a reference resource for the standard. This way it is ensured that the apps do not include vulnerabilities and technologies which are no longer relevant or existing in modern Android (and consequently in modern OWASP MAS) versions. The project uses Gradle with Kotlin DSL as its build automation tool. The core frameworks include the Android Framework, various APIs for Cryptography and AndroidX for backwards compatibility.

\subsubsection{Android Framework}
We use Activities and Services for User Interface logic and background processing. By default, user credentials are stored within SharedPreferences, that allow for a simple and native Android way to persistently store data. Intents are used for handling inter-component communication (ICC) \todo{maybe remove this acronym?}. Android Keystore provides a modern, safe and easy way for storing and managing cryptographic keys.

\subsubsection{APIs for Cryptography}
For cryptographic algorithms and operations we use both Java Cryptography Architecture (JCA) and Android-specific cryptography APIs. JCA is used as a less secure alternative to Android-specific APIs, which makes sense for designing security vulnerabilities. Besides operations such as key generation, encryption and signature, JCA is also useful for implementing cryptographic features deemed deprecated and insecure by Android-specific APIs, such as older Key Stores. The Android-specific APIs entail, for example, the Android Keystore System (\texttt{android.security.keystore.*}) for a hardware-backed native Android approach of managing cryptographic keys, and the Base64 API (\texttt{android.util.Base64}) for encoding keys.

\subsubsection{AndroidX Libraries}
The project makes use of AndroidX libraries to ensure the backwards compatibility of our apps with older Android versions. This is especially relevant since the apps are based on Android 15, a relatively new Android version. We use AppCompat (\texttt{androidx.appcompat}) for backwards-compatible UI elements, and all Activities extend \texttt{AppCompatActivity} to ensure our apps behave consistently and as intended across different Android API levels, especially the older ones.


\section{Vulnerabilities Selection Process}
At the time of writing, there are 117 vulnerabilities documented by OWASP MASWE, with two of them classified as deprecated. 

Of these 115 viable vulnerabilities, we decided to focus on those that have received little to no coverage in existing MASTG reference apps. Adding more variations of the same vulnerabilities that have already been covered by other apps can add value to the existing reference app dataset, but only if these variations differ sufficiently from existing implementations. By focusing on vulnerabilities with little to no previous coverage, we can ensure that the vulnerabilities implemented in our apps are unique and add to both the educational value of the MASTG reference apps and the usefulness of the reference apps for benchmarking mobile application security analysis tools.

We decided to work on one category at a time, since it appears more sensible for both educational and tool testing reasons to have a few categories covered completely instead of touching on many categories but only to little extend. Because the apps are standalone units that can be run, analyzed and tested independently, it makes sense to have a few apps entailing an implementation for each of the app specific vulnerabilities, instead of many apps which individually provide little value.

In terms of which categories to start with, we decided to first focus on MASVS-STORAGE. With only six storage vulnerabilities described by OWASP, it has the smallest amount of vulnerabilities to implement, making it a good starting place. MASVS-STORAGE exclusively deals with Android-native features, which creates a useful environment for getting more familiar with the Android ecosystem and functionalities. 

Afterwards, we shift our focus to categories that fit our system architecture and existing implementations the most, while still having a large amount of vulnerabilities with little to no previous coverage by other apps. Because of these criteria, we decided to implement MASVS-CRYPTO next, as it fits nicely into our template approach without needing many adjustments to the code of our project, and has one of the worst covered to possible vulnerability ratios, with only 2 of 19 possible MASVS-CRYPTO vulnerabilities having seen previous coverage.
