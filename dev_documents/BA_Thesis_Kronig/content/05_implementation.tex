To implement this vulnerability, we make use of the \texttt{onRegister} hook to call two methods whenever a new user registers. The first method writes the user credentials to system logs, while the second writes them to app logs, as shown in \ref{lst:onregister}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption=User registration hook invoking logging of sensitive credentials, label=lst:onregister]
@Override
protected void onRegister(String email, String password) {
    userDataToSystemLogs(email, password);
    userDataToAppLogs(email, password);
}
\end{lstlisting}

\noindent
For system logs, we make use of the command-line tool \texttt{Logcat}, as shown in \ref{lst:systemlogs}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption=Writing user credentials to system logs using logcat, label=lst:systemlogs]
private void userDataToSystemLogs(String email, String password){
    Log.d(LOG_TAG, "New User registered");
    Log.d(LOG_TAG, "User E-Mail: "+ email);
    Log.d(LOG_TAG, "User Password: " + password);
}
\end{lstlisting}

\noindent
\ref{lst:applogs} shows the second method, takes the user credentials and writes them to the apps internal file system, which are part of its app logs.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption=Writing user credentials to application log files, label=lst:applogs]
private void userDataToAppLogs(String email, String password){
    try {
        File logFile = new File(getFilesDir(), CREDENTIALS_FILE_NAME + ".txt");
        FileWriter writer = new FileWriter(logFile, true);
        writer.append("Login - Username: ")
                .append(email)
                .append(", Password: ")
                .append(password)
                .append("\n");
        writer.close();
        Log.d(LOG_TAG, "Logged credentials to app logs");
    } catch (IOException e) {
        Log.e(LOG_TAG, "Error writing to log file: " + e.getMessage());
    }
}
\end{lstlisting}

The challenge of implementing this vulnerability stemmed from the fact that global file permissions are not allowed by Android in newer versions \todo{Add here after which versions this is the case exactly}. For example, setting the permissions of any file, even using modern syntax, as seen in \ref{lst:Maswe0002SettingFilePermissions}, will be ignored by built-in Android security checks.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Setting a files permissions to world read and writeable}, label=lst:Maswe0002SettingFilePermissions]
file.setReadable(true, false);  
file.setWritable(true, false);
\end{lstlisting}

To still implement this vulnerability, we made use of an custom FileProvider which attempts to share access to the file with anybody, without checking their permissions to do so, as seen in \ref{lst:Maswe0002FileProvider}.

% XML Code
\begin{lstlisting}[float=tbh, style=XMLStyle, mathescape=true, captionpos=b, caption={Custom FileProvider that grants Uri permissions without checking access permissions}, label=lst:Maswe0002FileProvider]

    android:name="androidx.core.content.FileProvider"
    android:authorities="com.dkronig.maswe_storage.CustomFileProvider"
    android:exported="false"
    android:grantUriPermissions="true"
    android:permission="" >
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_paths" />
</provider>
\end{lstlisting}

This FileProvider is then called every time a new user registers by hooking into the onRegister method. We first create a new Uri for accessing the file storing the user credentials. It then creates a new intent for sharing, attaches the file in plaintext and prompts the user to share it with any app of his/her \todo{Figure out how to gender properly} choosing. This can be seen in \ref{lst:Maswe0002PromptingUserShareCredentials}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Prompting the user to share a plaintext file containing user credentials}, label=lst:Maswe0002PromptingUserShareCredentials]
@Override
protected void onRegister(String email, String password) {
    Uri uri = FileProvider.getUriForFile(
            this,
            this.getPackageName() + ".CustomFileProvider",
            new File(this.getFilesDir(), "maswe_0002_user_credentials.txt"));

    Intent share = new Intent(Intent.ACTION_SEND);
    share.setType("text/plain");
    share.putExtra(Intent.EXTRA_STREAM, uri);
    share.addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION);
    startActivity(Intent.createChooser(share, "Share file via"));
}
\end{lstlisting}

This approach is less dangerous than setting file permissions directly, since it makes the user aware of the issue, and can only cause a breach of sensitive user data if the user him/herself \todo{gender this properly} chooses to do so. We decided to settle on this approach, since it appeared impossible to implement this vulnerability more directly on new Android versions.

To implement this vulnerability, we first create a new MediaStore entry to store future user credentials in \ref{lst:Maswe0007CreateMediaStoreEntry}.

    values.put(MediaStore.MediaColumns.MIME_TYPE, "text/plain");

We implement this vulnerability in three different ways. Generating the cryptographic key used for encryption and decryption of user credentials is done using pseudo-random numbers with very little randomness. The cryptographic key that is generated is of insufficient length and is used for a broken encryption algorithm.

For generating our encryption key, we use a custom source of randomness, as seen in \ref{lst:Maswe0009RandomGeneration}. For this, we use a very predictable seed that is hard-coded into the \texttt{EncryptionHandler.java} file, which manages the entire encryption process. For generating pseudo-random numbers from this seed, we then use SHA1PRNG, which is extremely outdated.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Custom source of pseudo-random numbers using a predictable, hard-coded seed and outdated PRNG algorithm}, label=lst:Maswe0009RandomGeneration]
// Very predictable seed for key generation, very low entropy
byte[] keySeed = "01234567".getBytes(StandardCharsets.UTF_8);

// SHA1PRNG is a very old pseudorandom number generator
SecureRandom random = SecureRandom.getInstance("SHA1PRNG");
random.setSeed(keySeed);
\end{lstlisting}

This predictable source of pseudo-random numbers is then used to generate our cryptographic key, as seen in \ref{lst:Maswe0009KeyGeneration}. For the cryptographic algorithm, we chose DES (Data Encryption Standard), which is an old and broken cryptographic algorithm. Broken here means that the encryption created by DES can be cracked by modern devices, rendering it obsolete. In addition to this, we specify the DES key to be of 56-bit length. This, together with our not so random source of pseudo-random numbers, poses a great threat to the functionality of the encryption used here, even if a modern cryptographic algorithm had been chosen in place of DES.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Generating a DES cryptographic key of bit-length 56 using the source of randomness created above}, label=lst:Maswe0009KeyGeneration]

secretKey = keyGenerator.generateKey();

KeyGenerator keyGenerator = KeyGenerator.getInstance("DES");
\end{lstlisting}

For this vulnerability, we decided to use PBKDF2 (Password-Based Key Derivation Function 2) to derive an AES (Advanced Encryption Standard) key, which is then used for encrypting and decrypting user credentials of the app. Both PBKDF2 and AES are considered secure if used properly. Since this vulnerability is about improper derivation of the cryptographic key, we focused on making the derivation process as exploitable and vulnerable as possible.

The idea behind PBKDF2 is to repeatedly hash a password into a strong cryptographic key. Adding a salt, which is a random and unique value added to the initial password, and repeating the hash process for a large number of iterations are required to make PBKDF2 cryptographically secure.

For our PBKDF2 key derivation, we use a combination of vulnerable parameters, as seen in \ref{lst:Maswe0010KeyDerivation}. We use only 10 hashing iterations, whereas the recommended amount of iterations for secure usage in 2025 is 300,000 or more. For the salt, we use a hard-coded, static 16 byte array of 0's, making the salting process useless. Combining this with the use of a weak, hard-coded password for the hashing process means that the PBKDF2 key derivation implemented here is completely insecure, making the AES key used for encrypting user credentials easily retrievable for any attacker.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Derivation of AES key using PBKDF2}, label=lst:Maswe0010KeyDerivation]
private static final int ENCRYPTION_ITERATIONS = 10;
private static final int KEY_LENGTH = 128;
private static final byte[] SALT = new byte[16];
private static SecretKey secretKey;
private static final String PASSWORD_FOR_KEY_DERIVATION = "password";


public static void setupEncryption() throws Exception {
    PBEKeySpec secretKeySpec = new PBEKeySpec(
        PASSWORD_FOR_KEY_DERIVATION.toCharArray(), 
        SALT,
        ENCRYPTION_ITERATIONS, 
        KEY_LENGTH);
    SecretKeyFactory secretKeyFactory = SecretKeyFactory
            .getInstance("PBKDF2WithHmacSHA256");
    byte[] keyBytes = secretKeyFactory.generateSecret(secretKeySpec).getEncoded();

    // Generate the secret key
    secretKey = new SecretKeySpec(keyBytes, "AES");
}
\end{lstlisting}
