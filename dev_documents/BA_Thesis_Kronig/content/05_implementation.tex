\chapter{Implementation}
\label{c:implementation}

This chapter describes the concrete technical implementations of the selected MASWE vulnerability types. For each implementation, only code excerpts and architectural ideas relevant to the vulnerability are discussed instead of showing and going over the complete source code. Code that is not of relevance to the vulnerability is omitted and indicated as such. The complete source code is available on our GitHub repository \cite{ba_thesis_github_repository}. The chapter is structured according to the MASVS categories, and the vulnerabilities are sorted in the same way as done by OWASP MASWE.

To implement this vulnerability, we made use of the \texttt{onRegister} hook to call two methods whenever a new user registers. The first method writes the user credentials to system logs, while the second writes them to app logs, as shown in Listing \ref{lst:onregister}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption=User registration hook invoking logging of sensitive credentials., label=lst:onregister]
@Override
protected void onRegister(String email, String password) {
    userDataToSystemLogs(email, password);
    userDataToAppLogs(email, password);
}
\end{lstlisting}

\noindent
For system logs, we make use of the command-line tool \texttt{Logcat}, as shown in Listing \ref{lst:systemlogs}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption=Writing user credentials to system logs using logcat., label=lst:systemlogs]
private void userDataToSystemLogs(String email, String password){
    Log.d(LOG_TAG, "New User registered");
    Log.d(LOG_TAG, "User E-Mail: "+ email);
    Log.d(LOG_TAG, "User Password: " + password);
}
\end{lstlisting}

\noindent
Listing \ref{lst:applogs} shows the second method. It takes the user credentials and writes them to the app's internal file system, which is part of its app logs.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption=Writing user credentials to application log files., label=lst:applogs]
private void userDataToAppLogs(String email, String password){
    try {
        File logFile = new File(getFilesDir(), CREDENTIALS_FILE_NAME + ".txt");
        FileWriter writer = new FileWriter(logFile, true);
        writer.append("Login - Username: ")
                .append(email)
                .append(", Password: ")
                .append(password)
                .append("\n");
        writer.close();
        Log.d(LOG_TAG, "Logged credentials to app logs");
    } catch (IOException e) {
        Log.e(LOG_TAG, "Error writing to log file: " + e.getMessage());
    }
}
\end{lstlisting}

The challenge of implementing this vulnerability stemmed from the fact that global file permissions have not been allowed by Android since Android 7.0 (API 24) \cite{android_deprecated_world_file_permissions}. For example, attempting to set the permissions of any file to world-writable or readable, as shown in Listing \ref{lst:Maswe0002SettingFilePermissions}, will cause built-in Android security checks to throw a \texttt{SecurityException}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Attempting to set permissions of a file to world read and writable.}, label=lst:Maswe0002SettingFilePermissions]
SharedPreferences sharedPreferences = getSharedPreferences("maswe_0002_user_credentials", 
    Context.MODE_WORLD_READABLE |  Context.MODE_WORLD_WRITABLE);
\end{lstlisting}

To still implement this vulnerability, we made use of a custom \texttt{FileProvider}. This \texttt{FileProvider} attempts to share access to the file containing user credentials with anybody, without checking their permissions to do so. The relevant code for this is shown in Listing \ref{lst:Maswe0002FileProvider}.

% XML Code
\begin{lstlisting}[float=tbh, style=XMLStyle, mathescape=true, captionpos=b, caption={Custom \texttt{FileProvider} that grants \texttt{Uri} permissions without checking access permissions.}, label=lst:Maswe0002FileProvider]
<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="com.dkronig.masvs_storage.CustomFileProvider"
    android:exported="false"
    android:grantUriPermissions="true"
    android:permission="" >
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_paths" />
</provider>
\end{lstlisting}

This \texttt{FileProvider} is called every time a new user registers by hooking into the \texttt{onRegister} method. We first create a new \texttt{Uri} for accessing the file storing the user credentials. It then creates a new \texttt{Intent} for sharing, attaches the file in plaintext, and prompts the user to share it with any app of their choosing. The calling of the \texttt{FileProvider} is shown in Listing \ref{lst:Maswe0002PromptingUserShareCredentials}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Prompting the user to share a plaintext file containing user credentials.}, label=lst:Maswe0002PromptingUserShareCredentials]
@Override
protected void onRegister(String email, String password) {
    Uri uri = FileProvider.getUriForFile(
            this,
            this.getPackageName() + ".CustomFileProvider",
            new File(this.getFilesDir(), "maswe_0002_user_credentials.txt"));

    Intent share = new Intent(Intent.ACTION_SEND);
    share.setType("text/plain");
    share.putExtra(Intent.EXTRA_STREAM, uri);
    share.addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION);
    startActivity(Intent.createChooser(share, "Share file via"));
}
\end{lstlisting}

This approach is less dangerous than setting file permissions directly, as it makes the user aware of the issue by directly prompting them to share the file. A breach of sensitive user data can only occur if the user chooses to share the credentials with third parties. We decided to settle on this approach since it did not appear feasible to implement this vulnerability more directly on new Android versions.

Android does not enforce any encryption of backups made by Android applications. Instead, it checks whether the backup is encrypted and only proceeds with the backup process if this is the case. To counter this and implement the vulnerability, we specifically set the flag shown in Listing \ref{lst:xmlbackup} to false. This ensures that Android does not hinder the backup from happening, allowing us to back up sensitive user data in plaintext. Part of the backup is the entire \texttt{SharedPreferences} directory, which includes \texttt{maswe\_0003\_user\_credentials.xml}. This file contains the login credentials of everybody that used the \texttt{RegisterActivity.java} of this vulnerability.

\begin{lstlisting}[float=tbh, style=XMLStyle, mathescape=true, captionpos=b, caption={Backup rules for maswe\_0003.}, label=lst:xmlbackup]
<cloud-backup disableIfNoEncryptionCapabilities="false">
    <include domain="sharedpref" path="."/>
</cloud-backup>
\end{lstlisting}

We further ensured that client side encryption of the backup is not enforced by excluding the flag \lstinline|<... requireFlags="clientSideEncryption"/>| for each include statement. This is done for both the cloud backup and device-to-device transfer.

Writing to shared storage without user interaction has become increasingly difficult in newer Android versions. However, it is still possible to do so using \texttt{MediaStore}. \texttt{MediaStore} files are not part of the sandboxed app environment and are visible to all other apps on the device. If the reading permissions are not set properly, other apps are furthermore able to read the \texttt{MediaStore} files without restrictions. 

To implement this vulnerability, we first create a new \texttt{MediaStore} entry to store future user credentials in, as shown in Listing \ref{lst:Maswe0007CreateMediaStoreEntry}. We then write user credentials to this entry whenever a new user registers.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Creating a \texttt{MediaStore} entry and writing user credentials to it.}, label=lst:Maswe0007CreateMediaStoreEntry]
private void createMediaStoreEntry(){
    ContentValues values = new ContentValues();
    values.put(MediaStore.MediaColumns.DISPLAY_NAME, FILENAME);
    values.put(MediaStore.MediaColumns.MIME_TYPE, "text/plain");
    values.put(MediaStore.MediaColumns.RELATIVE_PATH, Environment.DIRECTORY_DOCUMENTS);

    fileUri = getContentResolver().insert(MediaStore.Files.
            getContentUri("external"), values);
}

private void writeToSharedStorage(String content) {
    try (OutputStream out = getContentResolver().openOutputStream(fileUri)) {
        assert out != null;
        out.write(content.getBytes());
        out.flush();
    } catch (IOException e) {
        e.printStackTrace();
    }
}
\end{lstlisting}

We implemented this vulnerability in three different ways. Generating the cryptographic key used for encryption and decryption of user credentials is done using pseudo-random numbers with very little randomness. The cryptographic key generated is of insufficient length and is furthermore used with an encryption algorithm considered broken.

For generating our encryption key, we used a custom source of randomness. This is shown in Listing \ref{lst:Maswe0009RandomGeneration}. For creating the source of randomness, we used a very predictable seed that is hard-coded into the \texttt{EncryptionHandler.java} file, which manages the entire encryption process. For generating pseudo-random numbers from this seed, we then use SHA1PRNG, which is extremely outdated.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Generating a DES key of short length using a weak pseudo-random number source and a hard-coded seed.}, label=lst:Maswe0009RandomGeneration]
private static final String ALGORITHM_PRNG = "SHA1PRNG";
private static final String KEY_SEED = "01234567";
private static final int DES_KEY_SIZE = 56;
    
private static SecretKey generateKey() throws Exception {
    byte[] keySeed = KEY_SEED.getBytes(StandardCharsets.UTF_8);

    SecureRandom random = SecureRandom.getInstance(ALGORITHM_PRNG);
    random.setSeed(keySeed);

    KeyGenerator keyGenerator = KeyGenerator.getInstance(ALGORITHM_DES);
    keyGenerator.init(DES_KEY_SIZE, random);

    return keyGenerator.generateKey();
}
\end{lstlisting}

This predictable source of pseudo-random numbers is then used to generate our cryptographic key, as shown in the same Listing \ref{lst:Maswe0009RandomGeneration}. For the cryptographic algorithm, we chose DES (Data Encryption Standard), which is an old and broken cryptographic algorithm. Broken here means that the encryption created by DES can be cracked by modern devices, rendering it obsolete. In addition to this, the DES key length is set to 56 bits. This, together with our insufficiently random source of pseudo-random numbers, poses a great threat to the functionality of the encryption used here, even if a modern cryptographic algorithm had been chosen in place of DES.

For this vulnerability, we decided to use Password-Based Key Derivation Function 2 (PBKDF2) to derive an Advanced Encryption Standard (AES) key, which is then used for encrypting and decrypting user credentials of the app. Both PBKDF2 and AES are considered secure if used properly. Since this vulnerability is about improper derivation of the cryptographic key, we focused on making the derivation process as exploitable and vulnerable as possible.

The idea behind PBKDF2 is to repeatedly hash a password into a strong cryptographic key. Adding a salt, which is a random and unique value added to the initial password, and repeating the hash process for a large number of iterations are required to make PBKDF2 cryptographically secure. For our PBKDF2 key derivation, we used a combination of vulnerable parameters, as shown in Listing \ref{lst:Maswe0010KeyDerivation}. We use only 10 hashing iterations, whereas the recommended number of iterations for secure usage in 2025 is 300,000 or more. For the salt, we use a hard-coded, static 16 byte array of 0's, making the salting process useless. Combining this with the use of a weak, hard-coded password for the hashing process means that the PBKDF2 key derivation implemented here is completely insecure, making the AES key used for encrypting user credentials easily retrievable by any attacker.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Derivation of an AES key using PBKDF2.}, label=lst:Maswe0010KeyDerivation]
private static final int ENCRYPTION_ITERATIONS = 10;
private static final int KEY_LENGTH = 128;
private static final byte[] SALT = new byte[16];
private static SecretKey secretKey;
private static final String PASSWORD_FOR_KEY_DERIVATION = "password";

private static SecretKey generateKey() throws Exception {
    PBEKeySpec secretKeySpec = new PBEKeySpec(
        PASSWORD_FOR_KEY_DERIVATION.toCharArray(), 
        SALT,
        ENCRYPTION_ITERATIONS, 
        KEY_LENGTH);

    SecretKeyFactory secretKeyFactory = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256");

    byte[] keyBytes = secretKeyFactory.generateSecret(secretKeySpec).getEncoded();
    SecretKey secretKey = new SecretKeySpec(keyBytes, "AES");

    return secretKey;
}
\end{lstlisting}

This vulnerability is not about adding an insecure feature but instead leaving a security feature (key rotation) out. To make the vulnerability more interesting, we added some additional security flaws to the implementation. The relevant code is shown in Listing \ref{lst:maswe0011NoRotationBks}. We use Rivest-Shamir-Adleman (RSA) for encrypting and decrypting user data. Because there is no key rotation, the RSA key will never become invalid and will not be replaced by a new and secure one. This means that if it ever falls into the hands of attackers, they could decrypt user data at will for an indefinite amount of time.

The additional security flaws consist of using the deprecated Bouncy Castle Keystore (\texttt{BKS}) to store our RSA key. The issues of using \texttt{BKS} for storing and managing our key are discussed at great length in the vulnerability implementation of Subsection \ref{subsec:maswe-0015}, which is about deprecated keystores. In short; our implementation of \texttt{BKS} allows attackers to retrieve the private RSA key, which turns the theoretical security concern that the missing key rotation poses into a practical and detrimental security problem.

\begin{lstlisting}[style=JavaStyle, float=tbh, captionpos=b, caption={Using \texttt{BKS} for RSA encryption with no key rotation.}, label={lst:maswe0011NoRotationBks}]
private static final String RSA_KEY_ALIAS = "maswe_0011_rsa_key";
private static final String KEYSTORE_FILE = "maswe_0011_keystore.bks";
private static final String KEYSTORE_PASSWORD = "Xk9$wR2!dF7pLq4Z";
private static final String KEY_PASSWORD = "S7v!Tz8#uK2qRj5M";
private static final String CIPHER_TRANSFORMATION = "RSA/ECB/PKCS1Padding";

public String encryptData(String plaintext) throws Exception {
    Cipher cipher = Cipher.getInstance(CIPHER_TRANSFORMATION, "BC");
    cipher.init(Cipher.ENCRYPT_MODE, getPublicKey());

    byte[] encrypted = cipher.doFinal(plaintext
                .getBytes(StandardCharsets.UTF_8));
    return Base64.encodeToString(encrypted, Base64.NO_WRAP);
}

private static PublicKey getPublicKey() throws Exception {
    if (keyStore == null) throw new IllegalStateException("Keystore not loaded");
    return keyStore.getCertificate(RSA_KEY_ALIAS).getPublicKey();
}
\end{lstlisting}

We implemented this vulnerability by using the same cryptographic key for multiple different purposes. These include the encryption and decryption of user credentials, as well as signing and verifying messages. RSA was chosen as the cryptographic algorithm because it relies on a long-lived key that typically remains valid and in use for an extended duration. This makes it even worse if our overloaded key is compromised.

As shown in Listing \ref{lst:Maswe0012CreatingKey}, we ensured that only RSA is used for message digests involved in the signing and verification process of signatures. Furthermore, RSA with Public-Key Cryptography Standards \#1 (PKCS\#1) v1.5 padding is used for encrypting and decrypting data. This makes the encryption vulnerable to oracle attacks, such as the Bleichenbacher attack \cite{bleichenbacher1998}. If this key were to fall into an attacker's hands, the attacker would be able to decrypt all existing user credentials and otherwise encrypted data. The attacker could furthermore forge message signatures and feed malicious data to the app.

To introduce the risk of the users themselves leaking sensitive data, we removed any text obfuscation on input fields for user passwords both in \texttt{LoginActivity.java} and \texttt{RegisterActivity.java}. The code for this is shown in Listing \ref{lst:Maswe0053ObfuscationRemoved}. Additionally, we disabled all screenshot and screen recording protections. 

\begin{lstlisting}[style=JavaStyle, float=tbh, captionpos=b, caption={Removing text obfuscation and adding auto complete and auto correct flags for user input fields.}, label={lst:Maswe0053ObfuscationRemoved}]
private void removeObfuscation(){
    EditText email_field = findViewById(R.id.et_email);
    EditText password_field = findViewById(R.id.et_password);

    password_field.setInputType(InputType.TYPE_CLASS_TEXT |
            InputType.TYPE_TEXT_FLAG_AUTO_COMPLETE |
            InputType.TYPE_TEXT_FLAG_AUTO_CORRECT);

    email_field.setInputType(InputType.TYPE_TEXT_FLAG_AUTO_COMPLETE |
            InputType.TYPE_TEXT_FLAG_AUTO_CORRECT);

    password_field.setCustomSelectionActionModeCallback(null);
}
\end{lstlisting}

By enabling copy and paste functionalities for the password field, any text that is copied or cut from the input field will be stored in the \texttt{Android Clipboard}. Data stored in the \texttt{Android Clipboard} is not confined to the app's sandbox and is accessible by all apps running in the foreground. This holds true even on newer Android versions \cite{secure_clipboard_handling}. This means that an attacker can run a service from a malicious app installed on the device that accesses data from the \texttt{Android Clipboard}, potentially reading and stealing sensitive user data.

The core of this vulnerability's implementation comes from the code snippet of our custom content provider shown in Listing \ref{lst:Maswe0064GrantingFilePermissions}. The vulnerability comes from the fact that \texttt{uri.getLastPathSegment()} extracts the user-given file \texttt{URI} without any validation in place. The content provider tries to find the file, construct its full path and return a file descriptor granting reading permissions to the file. For all of this, the content provider directly uses the unsanitized user input.

\begin{lstlisting}[style=JavaStyle, float=tbh, captionpos=b, caption={Custom \texttt{ContentProvider} granting reading permission to user-requested file without path traversal checks or sanitizing the input.}, label={lst:Maswe0064GrantingFilePermissions}]
@Override
public ParcelFileDescriptor openFile(Uri uri, String mode) throws FileNotFoundException {
    String fileName = uri.getLastPathSegment();

    if (fileName == null) {
        throw new FileNotFoundException("No file name specified in URI");
    }

    File file = new File(getContext().getFilesDir(), fileName);
    return ParcelFileDescriptor.open(file, ParcelFileDescriptor.MODE_READ_ONLY);
}
\end{lstlisting}

This allows for path traversal attacks by using path traversal sequences such as \texttt{../}. Without it, the content provider would only be able to provide access to files stored within the \texttt{/files/*} directory. This way, an attacker can access and read any of the app's files, given that they have access to the custom content provider.
To ensure this is the case and further extend the impact of this vulnerability, the content provider is set to be exported in the \texttt{AndroidManifest.xml} of this app, as shown in Listing \ref{lst:Maswe0064ExportedProvider}. By leaving the \texttt{permission} parameter empty, we enforce that no permissions are required by other apps to access this app's content provider.

\begin{lstlisting}[style=XMLStyle, float=tbh, captionpos=b, caption={Exporting the custom \texttt{ContentProvider}, making it accessible to other apps without enforcing permissions.}, label={lst:Maswe0064ExportedProvider}]
<provider
    android:name="com.dkronig.masvs_platform.maswe_0064.CustomContentProvider"
    android:authorities="com.dkronig.masvs_platform.CustomContentProvider"
    android:exported="true"
    android:permission=""
    tools:ignore="ExportedContentProvider" />
\end{lstlisting}

This, in combination with the unsanitized content provider, means that any malicious app installed on the same device can trivially access any of the app's files, either directly or via path traversal. This is demonstrated in Listing \ref{lst:Maswe0064AccessingFilesExample}.

\begin{lstlisting}[style=JavaStyle, float=tbh, captionpos=b, caption={Accessing and reading files containing sensitive user data from malicious apps, both directly and using path traversal.}, label={lst:Maswe0064AccessingFilesExample}]
// Direct file access 
Uri.parse("content://com.dkronig.masvs_platform.CustomContentProvider
    /maswe_0064_user_credentials.txt"); 
InputStream in = getContentResolver().openInputStream(uri); 

// Read files via path traversal
Uri uri = Uri.parse("content://com.dkronig.masvs_platform.CustomContentProvider
    /../databases/app.db"); 
InputStream in = getContentResolver().openInputStream(uri);
\end{lstlisting}
