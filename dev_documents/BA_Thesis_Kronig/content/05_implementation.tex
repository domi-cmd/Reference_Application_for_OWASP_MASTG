To implement this vulnerability, we make use of the \texttt{onRegister} hook to call two methods whenever a new user registers. The first method writes the user credentials to system logs, while the second writes them to app logs, as shown in \ref{lst:onregister}.

% Java Code
\begin{lstlisting}[float=tbh, mathescape=true, captionpos=b, caption=User registration hook invoking logging of sensitive credentials, label=lst:onregister]
@Override
protected void onRegister(String email, String password) {
    userDataToSystemLogs(email, password);
    userDataToAppLogs(email, password);
}
\end{lstlisting}

\noindent
For system logs, we make use of the command-line tool \texttt{Logcat}, as shown in \ref{lst:systemlogs}.

% Java Code
\begin{lstlisting}[float=tbh, mathescape=true, captionpos=b, caption=Writing user credentials to system logs using logcat, label=lst:systemlogs]
private void userDataToSystemLogs(String email, String password){
    Log.d(LOG_TAG, "New User registered");
    Log.d(LOG_TAG, "User E-Mail: "+ email);
    Log.d(LOG_TAG, "User Password: " + password);
}
\end{lstlisting}

\noindent
\ref{lst:applogs} shows the second method, takes the user credentials and writes them to the apps internal file system, which are part of its app logs.

% Java Code
\begin{lstlisting}[float=tbh, mathescape=true, captionpos=b, caption=Writing user credentials to application log files, label=lst:applogs]
private void userDataToAppLogs(String email, String password){
    try {
        File logFile = new File(getFilesDir(), CREDENTIALS_FILE_NAME + ".txt");
        FileWriter writer = new FileWriter(logFile, true);
        writer.append("Login - Username: ")
                .append(email)
                .append(", Password: ")
                .append(password)
                .append("\n");
        writer.close();
        Log.d(LOG_TAG, "Logged credentials to app logs");
    } catch (IOException e) {
        Log.e(LOG_TAG, "Error writing to log file: " + e.getMessage());
    }
}
\end{lstlisting}

The challenge of implementing this vulnerability stemmed from the fact that global file permissions are not allowed by Android in newer versions \todo{Add here after which versions this is the case exactly}. For example, setting the permissions of any file, even using modern syntax, as seen in \ref{lst:Maswe0002SettingFilePermissions}, will be ignored by built-in Android security checks.

% Java Code
\begin{lstlisting}[float=tbh, mathescape=true, captionpos=b, caption={Setting a files permissions to world read and writeable}, label=lst:Maswe0002SettingFilePermissions]
file.setReadable(true, false);  
file.setWritable(true, false);
\end{lstlisting}

To still implement this vulnerability, we made use of an custom FileProvider which attempts to share access to the file with anybody, without checking their permissions to do so, as seen in \ref{lst:Maswe0002FileProvider}.

% XML Code
\begin{lstlisting}[float=tbh, language=XML, mathescape=true, captionpos=b, caption={Custom FileProvider that grants Uri permissions without checking access permissions}, label=lst:Maswe0002FileProvider]
<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="com.dkronig.maswe_storage.CustomFileProvider"
    android:exported="false"
    android:grantUriPermissions="true"
    android:permission="" >
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_paths" />
</provider>
\end{lstlisting}

This FileProvider is then called every time a new user registers by hooking into the onRegister method. We first create a new Uri for accessing the file storing the user credentials. It then creates a new intent for sharing, attaches the file in plaintext and prompts the user to share it with any app of his/her \todo{Figure out how to gender properly} choosing. This can be seen in \ref{lst:Maswe0002PromptingUserShareCredentials}.

% Java Code
\begin{lstlisting}[float=tbh, mathescape=true, captionpos=b, caption={Prompting the user to share a plaintext file containing user credentials}, label=lst:Maswe0002PromptingUserShareCredentials]
@Override
protected void onRegister(String email, String password) {
    Uri uri = FileProvider.getUriForFile(
            this,
            this.getPackageName() + ".CustomFileProvider",
            new File(this.getFilesDir(), "maswe_0002_user_credentials.txt"));

    Intent share = new Intent(Intent.ACTION_SEND);
    share.setType("text/plain");
    share.putExtra(Intent.EXTRA_STREAM, uri);
    share.addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION);
    startActivity(Intent.createChooser(share, "Share file via"));
}
\end{lstlisting}

This approach is less dangerous than setting file permissions directly, since it makes the user aware of the issue, and can only cause a breach of sensitive user data if the user him/herself \todo{gender this properly} chooses to do so. We decided to settle on this approach, since it appeared impossible to implement this vulnerability more directly on new Android versions.

Android does not enforce any default encryption of backups made by Android applications. To counter this, Android, by default, checks whether the backup is encrypted and only proceeds with the backup process if this is the case. To counter this and implement the vulnerability, we specifically set the flag seen in \ref{lst:xmlbackup} to false.

\begin{lstlisting}[float=tbh, language=XML, mathescape=true, captionpos=b, caption={Backup rules for maswe\_0003}, label=lst:xmlbackup]
<cloud-backup disableIfNoEncryptionCapabilities="false">
    <include domain="sharedpref" path="."/>
    <include domain="file" path="maswe_0003_user_credentials.txt"/>
</cloud-backup>
\end{lstlisting}

We implemented this vulnerability by not only using a hard-coded key, which is stored in the same file where it is used, but also by using it in combination with DES (Data Encryption Standard), which is considered a broken and outdated encryption algorithm. This can be seen in the code snippet here \ref{lst:maswe0006brokenalgorithm}.

public class EncryptionHandler {
    private static final String ENCRYPTION_KEY = "EncryptK";
    private static final String ALGORITHM = "DES/ECB/PKCS5Padding";
    private static final String KEY_ALGORITHM = "DES";
    ...
\end{lstlisting}

We then use this weak encryption on user credentials upon registration and save this sensitive data in SharedPreferences (internal storage) \ref{lst:maswe0006brokenencryption}.

% Java Code
\begin{lstlisting}[float=tbh, mathescape=true, captionpos=b, caption=Using DES and a hard-coded encryption key for weak encryption, label=lst:maswe0006brokenencryption]

Writing to shared storage without user interaction has become increasingly difficult in newer Android versions. However, it is still possible to do so using MediaStore.  MediaStore files are not part of the sand-boxed app environment and can be accessed by any other app without restrictions. To implement this vulnerability, we first create a new MediaStore entry to store future user credentials in \ref{lst:Maswe0007CreateMediaStoreEntry}.

% Java Code
\begin{lstlisting}[float=tbh, mathescape=true, captionpos=b, caption={Creating a new MediaStore entry for storing user credentials}, label=lst:Maswe0007CreateMediaStoreEntry]
private void createMediaStoreEntry(){
    ContentValues values = new ContentValues();
    values.put(MediaStore.MediaColumns.DISPLAY_NAME, FILENAME);
    values.put(MediaStore.MediaColumns.MIME_TYPE, "text/plain");
    values.put(MediaStore.MediaColumns.RELATIVE_PATH, Environment.DIRECTORY_DOCUMENTS);

    fileUri = getContentResolver().insert(MediaStore.Files.
            getContentUri("external"), values);
}
\end{lstlisting}

We then write new user credentials to this entry whenever a new user registers, as seen in \ref{lst:Maswe0007WriteToMediaStore}.

% Java Code
\begin{lstlisting}[float=tbh, mathescape=true, captionpos=b, caption={Writing credentials of new users to MediaStore}, label=lst:Maswe0007WriteToMediaStore]
private void writeToSharedStorage(String content) {
    try (OutputStream out = getContentResolver().openOutputStream(fileUri)) {
        assert out != null;
        out.write(content.getBytes());
        out.flush();
    } catch (IOException e) {
        e.printStackTrace();
    }
}
\end{lstlisting}
