To implement this vulnerability, we make use of the \texttt{onRegister} hook to call two methods whenever a new user registers. The first method writes the user credentials to system logs, while the second writes them to app logs, as shown in \ref{lst:onregister}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption=User registration hook invoking logging of sensitive credentials, label=lst:onregister]
@Override
protected void onRegister(String email, String password) {
    userDataToSystemLogs(email, password);
    userDataToAppLogs(email, password);
}
\end{lstlisting}

\noindent
For system logs, we make use of the command-line tool \texttt{Logcat}, as shown in \ref{lst:systemlogs}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption=Writing user credentials to system logs using logcat, label=lst:systemlogs]
private void userDataToSystemLogs(String email, String password){
    Log.d(LOG_TAG, "New User registered");
    Log.d(LOG_TAG, "User E-Mail: "+ email);
    Log.d(LOG_TAG, "User Password: " + password);
}
\end{lstlisting}

\noindent
\ref{lst:applogs} shows the second method, which takes the user credentials and writes them to the apps internal file system, which is part of its app logs.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption=Writing user credentials to application log files, label=lst:applogs]
private void userDataToAppLogs(String email, String password){
    try {
        File logFile = new File(getFilesDir(), CREDENTIALS_FILE_NAME + ".txt");
        FileWriter writer = new FileWriter(logFile, true);
        writer.append("Login - Username: ")
                .append(email)
                .append(", Password: ")
                .append(password)
                .append("\n");
        writer.close();
        Log.d(LOG_TAG, "Logged credentials to app logs");
    } catch (IOException e) {
        Log.e(LOG_TAG, "Error writing to log file: " + e.getMessage());
    }
}
\end{lstlisting}

This FileProvider is then called every time a new user registers by hooking into the onRegister method. We first create a new Uri for accessing the file storing the user credentials. It then creates a new intent for sharing, attaches the file in plaintext and prompts the user to share it with any app of his/her \todo{Figure out how to gender properly} choosing. This can be seen in \ref{lst:Maswe0002PromptingUserShareCredentials}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Prompting the user to share a plaintext file containing user credentials}, label=lst:Maswe0002PromptingUserShareCredentials]
@Override
protected void onRegister(String email, String password) {
    Uri uri = FileProvider.getUriForFile(
            this,
            this.getPackageName() + ".CustomFileProvider",
            new File(this.getFilesDir(), "maswe_0002_user_credentials.txt"));

    Intent share = new Intent(Intent.ACTION_SEND);
    share.setType("text/plain");
    share.putExtra(Intent.EXTRA_STREAM, uri);
    share.addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION);
    startActivity(Intent.createChooser(share, "Share file via"));
}
\end{lstlisting}

This approach is less dangerous than setting file permissions directly, as it makes the user aware of the issue and can only cause a breach of sensitive user data if the user him/herself \todo{gender this properly} chooses to do so. We decided to settle on this approach since it did not appear feasible to implement this vulnerability more directly on new Android versions.

We implement this vulnerability in three different ways. Generating the cryptographic key used for encryption and decryption of user credentials is done using pseudo-random numbers with very little randomness. The cryptographic key that is generated is of insufficient length and is used for a broken encryption algorithm.

For generating our encryption key, we use a custom source of randomness, as seen in \ref{lst:Maswe0009RandomGeneration}. For this, we use a very predictable seed that is hard-coded into the \texttt{EncryptionHandler.java} file, which manages the entire encryption process. For generating pseudo-random numbers from this seed, we then use SHA1PRNG, which is extremely outdated.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Custom source of pseudo-random numbers using a predictable, hard-coded seed and outdated PRNG algorithm}, label=lst:Maswe0009RandomGeneration]
// Very predictable seed for key generation, very low entropy
byte[] keySeed = "01234567".getBytes(StandardCharsets.UTF_8);

// SHA1PRNG is a very old pseudorandom number generator
SecureRandom random = SecureRandom.getInstance("SHA1PRNG");
random.setSeed(keySeed);
\end{lstlisting}

This predictable source of pseudo-random numbers is then used to generate our cryptographic key, as seen in \ref{lst:Maswe0009KeyGeneration}. For the cryptographic algorithm, we chose DES (Data Encryption Standard), which is an old and broken cryptographic algorithm. Broken here means that the encryption created by DES can be cracked by modern devices, rendering it obsolete. In addition to this, we specify the DES key to be of 56-bit length. This, together with our not so random source of pseudo-random numbers, poses a great threat to the functionality of the encryption used here, even if a modern cryptographic algorithm had been chosen in place of DES.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Generating a DES cryptographic key of bit-length 56 using the source of randomness created above}, label=lst:Maswe0009KeyGeneration]

For this vulnerability, we decided to use PBKDF2 (Password-Based Key Derivation Function 2) to derive an AES (Advanced Encryption Standard) key, which is then used for encrypting and decrypting user credentials of the app. Both PBKDF2 and AES are considered secure if used properly. Since this vulnerability is about improper derivation of the cryptographic key, we focused on making the derivation process as exploitable and vulnerable as possible.

The idea behind PBKDF2 is to repeatedly hash a password into a strong cryptographic key. Adding a salt, which is a random and unique value added to the initial password, and repeating the hash process for a large number of iterations are required to make PBKDF2 cryptographically secure.

For our PBKDF2 key derivation, we use a combination of vulnerable parameters, as seen in \ref{lst:Maswe0010KeyDerivation}. We use only 10 hashing iterations, whereas the recommended amount of iterations for secure usage in 2025 is 300,000 or more. For the salt, we use a hard-coded, static 16 byte array of 0's, making the salting process useless. Combining this with the use of a weak, hard-coded password for the hashing process means that the PBKDF2 key derivation implemented here is completely insecure, making the AES key used for encrypting user credentials easily retrievable for any attacker.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Derivation of AES key using PBKDF2}, label=lst:Maswe0010KeyDerivation]
private static final int ENCRYPTION_ITERATIONS = 10;
private static final int KEY_LENGTH = 128;
private static final byte[] SALT = new byte[16];
private static SecretKey secretKey;
private static final String PASSWORD_FOR_KEY_DERIVATION = "password";


public static void setupEncryption() throws Exception {
    PBEKeySpec secretKeySpec = new PBEKeySpec(
        PASSWORD_FOR_KEY_DERIVATION.toCharArray(), 
        SALT,
        ENCRYPTION_ITERATIONS, 
        KEY_LENGTH);
    SecretKeyFactory secretKeyFactory = SecretKeyFactory
            .getInstance("PBKDF2WithHmacSHA256");
    byte[] keyBytes = secretKeyFactory.generateSecret(secretKeySpec).getEncoded();

    // Generate the secret key
    secretKey = new SecretKeySpec(keyBytes, "AES");
}
\end{lstlisting}

Our implementation of this vulnerability makes use of the BKS (Bouncy Castle Keystore) and the BC (Bouncy Castle Provider) for storing and managing the RSA key used for encrypting user credentials. The relevant code for this can be seen in \ref{lst:Maswe0015UsingBcAndBks}.

% Java Code
\begin{lstlisting}[style=JavaStyle, float=tbh, mathescape=true, captionpos=b, caption={Loading BC and using BKS for managing cryptographic keys}, label=lst:Maswe0015UsingBcAndBks]
// Load BouncyCastle once
static {
    if (Security.getProvider("BC") == null) {
        Security.addProvider(new BouncyCastleProvider());
    }
}

public static void loadBksKeystore(Context context) throws Exception {
    // If keystore has already been loaded, do nothing and return
    if(keyStore != null){
        return;
    }

    keyStore = KeyStore.getInstance("BKS", "BC");

    try(InputStream inputStream = context.getAssets().open(KEYSTORE_FILE)) {
        keyStore.load(inputStream, KEYSTORE_PASSWORD.toCharArray());
    }

Android considers BKS to be a deprecated keystore. A significant issue with BKS is that it is a file-based keystore, meaning that the keystore stores the keys in the \texttt{maswe\_0015\_keystore.bks} file, which is bundled with the APK and is easily extractable. This vulnerability has been implemented using low-level mathematical operations for the encryption and decryption of user credentials instead of any proper cryptographic operations.

We use a circular bit-shifting approach for encrypting and decrypting data, as seen in \ref{lst:Maswe0019Encryption}. For encryption, the string to be encrypted is turned into bytes. By removing any text obfuscation on input fields for user passwords \texttt{LoginActivity.java} and \texttt{RegisterActivity.java}, as well as not adding any screenshot or screen recording protection, we introduce the risk of the users themselves leaking sensitive data. The code for this can be seen in \ref{lst:Maswe0053ObfuscationRemoved}.

\begin{lstlisting}[style=JavaStyle, float=tbh, captionpos=b, caption={Removing text obfuscation and adding auto complete and auto correct flags for user input fields}, label={lst:Maswe0053ObfuscationRemoved}]
private void removeObfuscation(){
    EditText email_field = findViewById(R.id.et_email);
    EditText password_field = findViewById(R.id.et_password);

    password_field.setInputType(InputType.TYPE_CLASS_TEXT |
            InputType.TYPE_TEXT_FLAG_AUTO_COMPLETE |
            InputType.TYPE_TEXT_FLAG_AUTO_CORRECT);

    email_field.setInputType(InputType.TYPE_TEXT_FLAG_AUTO_COMPLETE |
            InputType.TYPE_TEXT_FLAG_AUTO_CORRECT);

    // Enabling copy and paste functionalities on the password field
    password_field.setCustomSelectionActionModeCallback(null);
}
\end{lstlisting}

By enabling copy and paste functionalities for the password field, any text that is copied or cut from the input field will be stored in the clipboard. Data stored in the clipboard is not sandboxed and acccessible by all apps running in the foreground, even on newer Android versions. This means that an attacker can run a service from a malicious app installed on the device that reads the data from the clipboard, potentially reading and stealing sensitive user data.

The core of this vulnerability's implementation comes from this code snippet of the custom content provider \ref{lst:Maswe0064GrantingFilePermissions}. The issue is that \texttt{uri.getLastPathSegment()} extracts the user-given file URI without any validation in place. The content provider tries to find the file, construct its full path and return a file descriptor granting reading permissions to said file. For all of this, the content provider directly uses the unsanitized user input.

\begin{lstlisting}[style=JavaStyle, float=tbh, captionpos=b, caption={Custom content provider granting reading permission to user-requested file without path traversal checks or sanitizing the input}, label={lst:Maswe0064GrantingFilePermissions}]
@Override
public ParcelFileDescriptor openFile(Uri uri, String mode) throws FileNotFoundException {
    String fileName = uri.getLastPathSegment();

    if (fileName == null) {
        throw new FileNotFoundException("No file name specified in URI");
    }

    File file = new File(getContext().getFilesDir(), fileName);
    return ParcelFileDescriptor.open(file, ParcelFileDescriptor.MODE_READ_ONLY);
}
\end{lstlisting}

This allows for path traversal attacks by using path traversal sequences such as \texttt{../}. Without it, the content provider would only be able to provide access to files stored within the \texttt{/files/*} directory. This way, an attacker can access and read any of the app's files, given that they have access to the custom content provider.
To ensure this is the case and further extend the impact of this vulnerability, the content provider is set to be exported in the \texttt{AndroidManifest.xml} of this app, as seen in \ref{lst:Maswe0064ExportedProvider}. By leaving the permission parameter empty, we enforce that no permissions are required by other apps to access this app's content provider.

\begin{lstlisting}[style=XMLStyle, float=tbh, captionpos=b, caption={Exporting the custom content provider, making it accessible to other apps without enforcing permissions}, label={lst:Maswe0064ExportedProvider}]
<provider
    android:name="com.dkronig.maswe_platform.maswe_0064.CustomContentProvider"
    android:authorities="com.dkronig.maswe_platform.CustomContentProvider"
    android:exported="true"
    android:permission=""
    tools:ignore="ExportedContentProvider" />
\end{lstlisting}

This, in combination with the unsanitized content provider, means that any malicious app installed on the same device can trivially access any of the apps files, either directly or via path traversal. This is demonstrated in the code snippet \ref{lst:Maswe0064AccessingFilesExample}.

\begin{lstlisting}[style=JavaStyle, float=tbh, captionpos=b, caption={Accessing and reading files containing sensitive user data from malicious apps, both directly and using path traversal}, label={lst:Maswe0064AccessingFilesExample}]
// Direct file access 
Uri.parse("content://com.dkronig.maswe_platform.CustomContentProvider
    /maswe_0064_user_credentials.txt"); 
InputStream in = getContentResolver().openInputStream(uri); 

// Read files via path traversal
Uri uri = Uri.parse("content://com.dkronig.maswe_platform.CustomContentProvider
    /../databases/app.db"); 
InputStream in = getContentResolver().openInputStream(uri);
\end{lstlisting}

Using this command, an attacker can inspect the apps shared preferences, SQLite databases, and internal storage at run-time. An attacker can, for example, learn more about the encryption in place for user credentials by creating new user profiles and analyzing the resulting ciphertexts.
